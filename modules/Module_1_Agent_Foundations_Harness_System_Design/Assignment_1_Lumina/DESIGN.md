# DESIGN.md — LUMINA

## Components

The UI is the provided React and Vite app, deployed on Vercel. The UI only ever talks to the gateway. The backend runs on Fly.io and uses a public Express gateway that routes to a private Express agent. We keep the agent completely private because it is the only component that holds our provider keys for Anthropic, the search provider, and OpenAI, so none of them are ever reachable from the internet. Search runs on Tavily by default, but it can be swapped to SerpApi through the SEARCH_PROVIDER setting with no code change. We also run the agent's jobs worker as a separate process from the same codebase. We split this out because embedding a massive PDF takes a lot of CPU and we never want it blocking a streaming answer.

Most of our state lives in a single MongoDB Atlas M0 cluster. It stores conversation threads, GridFS file uploads, and a job queue that the worker polls. It also holds user memories and document chunks with their vector embeddings. Document search is hybrid: a vector search and a BM25 text search run together and get fused with reciprocal rank fusion. The free M0 tier only allows three search indexes so we max them out on chunk vectors, chunk text, and memory vectors.

For the temporary state, the agent keeps an in-process LRU cache in front of a Mongo search cache that expires after six hours. We added the LRU because hot repeat queries can skip hitting the database entirely. The cache clears on restart but Mongo still has the data so it is not a big deal. Finally, every answer writes a run log and a request record to Mongo instead of local disk, since Fly wipes a machine's disk on redeploy. When we need to run the quality checker, we export those logs into the runs folder with npm run export:runs.

## Responsibilities

The UI is provided and only ever talks to the gateway. It just renders the interface and sends requests, and it holds no API keys and makes no logic decisions. The gateway is the only piece that actually talks to the browser. It handles CORS, rejects any request without an X-User-Id with a 401, and validates the payloads with Zod. It rate limits each X-User-Id at 120 requests per minute on the ask and upload routes only, since those are the two that cost money, so normal UI polling for document status never gets blocked. We picked 120 because the benchmark sends 40 asks at a concurrency of 4 plus deep runs and gold set questions all as one user, and a lower limit would turn our own benchmark into errors. It also rejects oversized file uploads immediately because we don't want huge files slowing down the internal network. It reuses an incoming request ID if there is one and only creates a new one if it is missing, so the same ID tracks the whole flow. It never calls the LLMs itself. It just passes the streaming response straight through to the frontend without buffering it.

The agent service is the only part of the system that holds provider keys. The main agent process handles all the AI work and external calls to Anthropic and the search provider. Before it sends a single byte of the stream, it checks everything it can know up front, like whether the thread exists and whether the user is over their deep search cap, so those come back as real 404 and 429 responses. It runs the tool loop and builds the numbered source list before streaming the first token. It is also the only piece that decides when the loop stops and records whether it finished, hit a cap, or errored. It follows the depth the client asked for and never changes it, and plan_research is completely blocked in the code for quick requests. A quick run gets 8 tool calls, and since recall_memory always uses one, that leaves 7 for searching and fetching. If a quick run hits its cap, the answer says it stopped early instead of pretending it finished. In auto mode with a Space selected, the model gets both web search and document search and can call either or both, while web and docs modes just restrict which tools it gets. When a Space is selected, the system prompt tells the model which documents are in it, so a question about those documents gets sent to document search. It runs recall_memory automatically at the start of every ask instead of leaving it up to the model, so saved preferences always carry into new threads. It also enforces the daily limit for deep runs, handles explicit memory saves, and writes the run logs.

Grounding is the agent's most important job. Only pages we actually fetched can become sources, and each source's snippet is a passage copied word for word from that page's text, never written by the model. Before the text goes to the LLM, we trim each page down to its most relevant passages, which also keeps quick answers under their cost budget. The numbered source list is final before the model starts writing, and as the answer streams out, any citation number that doesn't match a source gets dropped before it reaches the user and is logged. If every fetch fails, the answer falls back to the search snippets and the trace says so. If retrieval finds nothing at all, the answer says it couldn't find anything and cites nothing.

When a user makes a deep request the agent streams its research plan first before any retrieval starts so the user immediately sees what it decided to look into. It generates three to six sub-questions and runs them in parallel a few at a time. Deep runs get 24 tool calls. Planning and memory recall use two, which leaves 22 split evenly across the sub-questions, so four sub-questions get five calls each and six get three each. Each sub-question searches with its own text and fetches the top results directly instead of running its own LLM loop, so the LLM is only called twice, once to plan and once to write the answer. The sub-questions share a list of URLs that have already been claimed, so if one sub-question's top result was already fetched by another, it moves on to the next unclaimed result. That is how a deep run actually finds at least twice as many distinct sources as the same question run on quick, instead of related sub-questions collapsing into the same pages. All the calls count against one shared counter, and if it runs out, no new calls start, the answer is written from whatever was collected, and the run is marked as capped. Every trace step and source gets tagged with the specific sub-question it served. Web sources are deduplicated by URL and document chunks by document ID plus page, and everything is renumbered into one clean final list before the model starts writing. The deep answer opens with a direct answer, then a section for each sub-question, then what is still unknown.

Finally the worker process just turns uploads into searchable chunks. It handles the parsing, chunking, and OpenAI embeddings. It only marks a document as indexed after a test probe confirms it is actually searchable in the database. If a document fails for good, the worker marks it failed with an error message and deletes any chunks it already inserted, so nothing from a broken document can ever be cited. It handles all this background prep and never touches the live answer stream at all.

## Communication

The UI and gateway talk using standard HTTP and JSON for almost everything. When you actually ask a question we use Server-Sent Events instead of WebSockets because the answer only flows one way from the server to the browser. It is way simpler to set up and works easily through normal HTTP proxies. If the gateway goes down the UI health indicator turns red and any streaming answer just stops immediately.

The gateway talks to the agent over Fly's private network which keeps the agent completely hidden from the public internet. The gateway passes along the user and request IDs and pipes the SSE stream straight back to the UI. If the agent is down when a request comes in, the gateway returns a 502 and /health reports degraded. If it dies mid-answer, the gateway sends an error event and closes the stream. If a user closes their browser mid-answer the gateway cancels the upstream request. We do this because we want the agent to kill the LLM call immediately so we are not paying for tokens nobody will ever read. A cancelled run is logged as an error with the message "client disconnected", since done, cap, and error are the only options and error is the honest one.

For external APIs the agent hits Anthropic and the search provider over HTTPS. We handle failures differently depending on the severity. If a single webpage fetch times out it just logs a failed trace step and the agent keeps searching other pages. But if the main LLM or search provider crashes the whole run ends as an error, either a 502 or an error event if the answer had already started streaming. No done event follows an error, and the run log records it as terminated with an error. For data the agent connects to Mongo directly. If the main database goes down the requests fail with a 502. But if just the search cache read fails we log it and treat it as a cache miss so we can keep generating the answer, and the log makes sure a broken cache never hides behind a low hit rate.

The agent and worker processes never actually talk to each other directly. They only communicate through a job queue in Mongo. When you upload a file the agent saves it to GridFS, drops a job in the queue, and returns a 202 accepted status right away. The worker constantly polls the queue and claims jobs atomically so two workers never grab the same file. While it works, the worker keeps updating a heartbeat on the job. If the worker crashes, the heartbeat stops and the document stops moving at whatever stage it was on, like parsing or embedding. A job only counts as stale after two minutes with no heartbeat, so a slow PDF that is still being processed never gets grabbed twice. When a stale job gets reclaimed, it picks up from the last finished stage, and chunk IDs are built from the document ID plus the chunk's position so a retry overwrites chunks instead of duplicating them. After three failed attempts, including OpenAI embedding errors, the document itself is marked failed with an error message. If no worker is alive at all, /health reports the worker's last heartbeat and shows degraded once it goes stale, so a dead worker shows up instead of documents just quietly freezing. The idea is that nothing fails silently: every failure shows up as a 502, an error event, a failed trace step, a document marked failed, or a degraded health check.

## State

We divide our database state into three main categories. Authoritative state is the data we cannot lose. This includes conversation threads, user memories, raw file uploads in GridFS, and the job queue. The daily deep search counter is also authoritative because it is what enforces the spend cap, so if it got wiped mid-day a user could run more deep searches than allowed. The check against the cap and the increment happen in one atomic database operation, so two deep requests arriving at the same time when a user is at four of five can't both get through. The count resets at the next UTC midnight, which is also the resetsAt time we send back with a 429. The run logs and request records in Mongo count as authoritative too because our grading scripts rely on them to evaluate the system. After we export them with npm run export:runs, a small step of our own moves any run that did not end as done into runs/failing/, which is also where we keep our deliberate failing trajectory. The agent owns threads, memories, the deep counter, and the run logs. It also creates document records and jobs, but the worker is the only one that updates their status. When a run finishes we save the answer with its sources. A capped run saves its partial answer marked as capped, and an errored run saves nothing that looks like an answer. Each message is saved as its own record with a timestamp, so several asks on the same thread at once can't overwrite each other. Every earlier turn in a thread goes into the prompt so a follow-up sees the whole conversation, but older answers get trimmed down so a long thread doesn't keep growing the cost of every answer.

Derived state like document chunks and vector embeddings can technically be rebuilt from the raw files. Losing them just costs us extra OpenAI API money and processing time. Finally we have caches like the in-process LRU and the Mongo search cache which we can wipe at any time. We compute /stats on the fly from the stored request records instead of keeping separate running counters for it, because we knew two sources of truth would eventually drift and the stats have to match the agent logs.

For data isolation every user record gets tagged with a user ID and chunks also get a space ID. We filter every query with these IDs so one person's private files can never accidentally leak into another user's answer. If someone asks about a Space that belongs to another user, they get a 404, so they can't even tell it exists. The one exception is the search cache, which is shared on purpose and keyed by the query and search provider, since a web search result is the same no matter who asked for it.

The trickiest part of the data flow is handling search consistency. MongoDB Atlas updates its search indexes asynchronously so there is a small delay where text chunks are saved in the database but will not show up in search results yet. The worker process handles this by never just trusting the database write. After inserting new chunks it runs a test search and only marks the document as fully indexed once that probe actually finds the data. The provided vector index can only filter by user and Space, not by document status, so the agent fetches a few extra results and then drops any chunks from documents that are not marked indexed yet. We built it this way because we never want the system to generate a broken citation from a half-indexed document.

## Trade-offs

We made a few big trade-offs to keep the system fast. Instead of writing a rule-based router we let the model do the routing. In auto mode with a Space selected, the model gets both web search and document search and decides which to call, or calls both when a question needs to blend our documents with what is on the web. We gave up some predictability here, because the model can occasionally send a question about our documents to the web instead, which is why the system prompt lists the Space's documents. But a fixed rule like docs first, web only if results are weak can never blend the two, and there is no reliable way to define weak when fused search scores are based on rank. We also made the first step of every quick run skip the model entirely. It searches the user's question as written and reads the top three pages in parallel with a 1.5 second timeout, and only then does the model decide whether to answer or keep searching. We gave up letting the model write its own first search query, but it cut our time to first token from 6.8 seconds to 3.8 seconds in testing, because most answers now need one model call instead of three.

We also run deep search sub-questions in parallel, a few at a time, instead of one after another. That is what keeps a deep search inside the 90 second target. The cost is that we are making several API calls at once, which gets us closer to provider rate limits, and the trace is harder to read because steps from different sub-questions show up interleaved. Tagging every step with its sub-question is what keeps it readable.

Our deep sub-questions also don't get their own LLM loops. Each one just searches and fetches, and the model only runs to plan and to write the final answer. That keeps a deep answer's cost predictable and makes the 24 call budget easy to split fairly, and at the benchmark's prices it should land somewhere around $0.12 to $0.15, well under the $0.35 cap. What we gave up is adaptivity. A sub-question with a bad search can't notice and try a better one, the way a real subagent could. It also means we are not going for the parallel subagents bonus.

We also had to make some tough calls around API costs. A deep search uses up a daily slot the moment it starts and resets at UTC midnight. We count it even if the run eventually errors out. It is a little unfair to the user if a failure is not their fault but we did it this way because a failed deep run still costs us money and a strict cap prevents people from gaming the system.

The one thing we are still really unsure about is skipping the re-ranker. A re-ranker adds another model call on every document question, and our whole quick answer has to show its first token within 2.5 seconds, so we left it out to protect that budget and keep costs down. But if our recall metric drops below 0.70 on the gold set it is going to be the first thing we add. We will not know for sure if we can get away without it until we actually run those evaluations.
